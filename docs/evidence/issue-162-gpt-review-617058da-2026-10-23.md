三、新發現的阻擋性 Finding
P1-17 — main 更新使完整驗證失效後，仍可能重新登記 GPT Final PASS

Priority：P1 · 狀態持久化／Release Gate 安全

相關檔案：

scripts/supplypilot_orchestrator.py L1152–1198

scripts/supplypilot_orchestrator.py L1891–1944

scripts/supplypilot_orchestrator.py L350–368

可觸發的情境

假設 Issue B 已完成完整 Gate，處於 WAITING_GPT_REVIEW，但尚未取得 Final PASS。

此時另一張 Issue A 合併到 main，並執行 state sync-main。

目前 _apply_main_sync() 會正確將 B 的 Verification 標為 STALE，也會將其 contract_verified 設為 False。

問題在於：B 的 implementation_state 仍可能維持 WAITING_GPT_REVIEW。

接著執行 state review-attest 時，程式主要檢查：

Issue 是否處於 WAITING_GPT_REVIEW。

Reviewed SHA 是否等於原本的 Feature HEAD。

GPT 審查證據與人工確認是否符合格式。

它沒有再次確認完整 Gate 是否仍有效，也沒有確認契約是否已失效。

因此，B 可能在完整驗證已經 STALE 的情況下，進入 GPT_FINAL_PASS。

can_open_pr() 同樣沒有重新檢查 Full Gate、main 基準及契約有效性。

影響

這是實際的 Release Gate 繞過風險：過期的完整驗證證據仍可能間接讓 Issue 取得建立 PR 的資格。

最小修正建議

在 state_attest_gpt_review() 重新核對持久化的完整驗證狀態、SHA、契約版本、main 與必要依賴。

can_open_pr() 也檢查這些 Release Gate 不變量，避免只依賴 GPT_FINAL_PASS 狀態。

當 main Sync 使 Issue 驗證失效時，讓它不能繼續停留在可直接取得 Final PASS 的有效審查狀態。

新增測試：Issue B 在 WAITING_GPT_REVIEW 時，Issue A 合併使 main 前進；即使 B 提供格式完全正確的 GPT Final PASS 證據，也必須拒絕登記，且 PR Gate 必須維持關閉。

這個缺口與 P1-15 不同：P1-15 是進入 Full Gate 前的契約核驗；P1-17 是完整驗證完成後、GPT 審查期間發生的狀態失效。
